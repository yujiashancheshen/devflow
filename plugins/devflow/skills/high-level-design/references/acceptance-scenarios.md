# 准入与验收场景规则

## 准入场景

使用 `AC-*` 编号，描述进入验收前必须通过的最小关键集合。优先覆盖核心正常流程、阻断主流程的关键异常、关键状态和禁止操作、会产生业务副作用的重复触发，以及适用的迁移、灰度、混部或回滚边界。

准入场景不替代详细测试用例，不展开接口字段穷举、性能脚本和故障注入步骤。

## 验收场景

使用 `VC-*` 编号，按需求目标和用户可感知功能组织，不按接口、数据表、MQ 或代码目录拆分。覆盖每个需求目标的核心结果，以及适用的角色、权限、入口、渠道、灰度范围、业务边界和历史数据表现。

## 编写要求

每个场景填写场景 ID、类型、前置条件、操作、可观察结果和验证层级。

- 可观察结果面向用户、运营、上下游或业务人员，不只写“写库成功”“发送 MQ 成功”或“功能正常”。
- 精确文案、枚举显示名和数值口径来自 PRD、设计源或已确认结论，不得臆造。
- 同一业务场景可以同时产生 AC 和 VC，但两者目的不同，不要复制两份相同内容。
- 存在阻塞问题时，受影响场景标记 `待确认` 并关联问题 ID。

可以用 EARS 语义检查触发条件和结果是否完整，但不要求把最终文档机械改写成固定句式。
