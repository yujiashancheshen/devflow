# 工作区与证据规则

## 工作区发现

- 当前执行目录是工作区，不要求自身是 Git 仓库；其中可以包含多个 Git 仓库、符号链接和需求材料。
- 用户未指定额外代码库时，只在当前工作区内搜索。
- 先检查当前目录，再检查直接子目录和符号链接目标中的 Git 仓库。结合需求关键词、项目结构、路由和模块名定位相关代码。
- 完成搜索仍无法定位相关代码时，向用户索取仓库路径、目标分支或模块范围，不要把“缺少代码路径”写成设计结论。

## 仓库边界

- 使用 `git rev-parse --show-toplevel` 确认 Git 根目录，以根目录名作为模块名。
- 模块类型只使用 `前端` 或 `后端`；Go 公共库和后端共享仓库归为 `后端`。
- 同一仓库既被依赖又需要改动时，两张表都出现，并把“依赖仓库是否改动”标为“是”。
- 没有跨仓依赖时保留依赖模块表头并写一行 `无`，使边界结论明确。

## 代码基线

每个相关仓库分别记录当前分支和 commit、工作区是否干净、核对范围、结论及证据位置。不要用一个仓库的基线代表多个仓库，也不要从目录名推断应用形态或职责。

## 证据状态

- `已核对-现有`：目标分支代码中存在。
- `待实现-新增`：需求明确要求新增，代码中尚不存在。
- `待实现-修改`：现状已核对，目标行为需要变化。
- `有冲突`：代码、PRD、接口资料或不同分支之间不一致。
- `待确认`：证据不足，无法形成概要结论。

代码证据写成 `<Git 仓库目录名>/<仓库内相对路径>:<符号或类型.字段>`。无法定位到符号时至少给出最接近的文件和核对结论，不要写“见代码”。

## 追踪矩阵

分析时维护 `需求目标 → Git 仓库 → 仓库内变化 → 跨仓契约 → 风险 → 准入/验收场景` 的关系，不要求机械地把矩阵全文写入产物。任何后续章节中新出现的改动仓库或依赖仓库，都要回填到需求概述的仓库表中。
