# 概要设计质量门

定稿前逐项检查，只有会改变仓库边界、关键数据口径、跨仓契约或上线风险的问题才阻断。

## 需求与范围

- 业务目标、范围和明确不做什么可以从文档直接识别。
- 已确认的需求结论已经落实，未确认问题没有被猜测成结论。
- 页面或交互发生变化时已有设计依据；不涉及前端时已有范围或代码依据。

## 仓库与证据

- 改动仓库、依赖仓库和职责边界可信，同一仓库没有被拆成多个“模块”。
- 现状来自目标分支真实代码，目标变化有 PRD、设计源或确认结论支持。
- 文档中的代码证据使用仓库名加仓内相对路径，没有本机绝对路径。

## 方案与契约

- 核心用户旅程、状态变化和跨仓数据流足以共同 Review。
- 只展开发生变化或存在风险的跨仓契约，变化内容、兼容策略和责任方完整。
- 未把字段全集、函数设计、完整 DDL、组件 API 或实现参数塞入概要设计。

## 风险与发布

- 历史数据、权限、事务、幂等、性能、迁移、定时任务、灰度、第三方依赖和高风险回滚按适用性检查。
- 发布顺序满足依赖关系，回滚方案说明代码、配置和已产生数据如何处理。
- 无依据的容量、重试、批量和阈值参数标记为待验证，没有被编造为事实。

## 验证闭环

- 至少存在一个 `AC-*` 准入场景和一个 `VC-*` 验收场景。
- 准入场景表达进入验收前的关键门槛，验收场景表达用户或业务可观察结果。
- 场景与需求目标、核心方案、契约变化和风险结论一致。
- 五章结构和轻量校验脚本通过。
