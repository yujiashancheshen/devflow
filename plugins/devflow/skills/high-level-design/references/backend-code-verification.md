## 目标

先还原当前代码契约，再根据需求设计目标契约。任何已有后端字段都必须能从代码定位，任何新增或修改字段都必须有目标需求依据。

## 证据优先级

按对象选择事实源，不使用一套资料覆盖所有场景：

| 要判断的内容 | 首选证据 | 辅助证据 |
|---|---|---|
| 当前路由、METHOD、PATH | 路由注册代码 | YApi、调用方代码 |
| 当前请求字段与必填性 | 请求 DTO、bind/validate tag、手工校验 | YApi、前端调用 |
| 当前响应字段与类型 | Response DTO、返回构造、序列化代码 | YApi、前端消费 |
| 当前统一响应信封 | 公共响应类型、中间件 | 接口样例 |
| 当前数据库结构 | 生效 DDL/迁移、模型与 ORM tag | 数据字典、旧设计 |
| 当前 MQ 契约 | 生产者 payload + 消费者解析 | 消息文档 |
| 目标新增/修改 | PRD、确认记录、设计结论 | YApi 草稿 |

代码不同来源互相冲突时，不机械套优先级。记录分支、commit 和冲突，判断哪份代码实际生效；无法判断则标记 `待确认`。

## 仓库与基线定位

1. 当前执行目录就是工作区，不要求自身是 Git 仓库。先检查当前目录，再搜索直接子目录和符号链接目标中的 Git 仓库。
2. 从用户给出的路径或工作区候选仓库开始，使用 Git 根目录定位命令确认仓库边界。
3. 根据需求关键词、模块名、路由、接口和项目结构筛选相关仓库，不能只搜索固定目录名，也不能因工作区根目录没有 `.git` 就停止。
4. 记录当前分支、commit 和工作区是否有相关未提交修改；多仓库分别记录。
5. 搜索项目级说明、路由入口、模块目录和生成代码来源。
6. 用户已有未提交修改可能属于目标设计或进行中的实现，不能擅自还原；在证据中标记“工作区版本”。
7. 完成工作区搜索仍无法定位相关代码时，使用交互式询问工具请用户提供仓库路径、分支或模块范围；不要直接产出“缺少代码仓库路径”的设计问题。

建议先建立；每行必须是一个 Git 仓库，仓库内 package、Service、Domain、处理器和任务不能拆成模块行：

| Git 仓库 | 模块类型 | 分支 | Commit/工作区 | 入口目录 | 备注 |
|---|---|---|---|---|---|

`Git 仓库` 填写经 Git 根目录定位命令确认的根目录名；本参考用于后端核对，`模块类型` 固定填 `后端`。

## HTTP 与 RPC 核对

### 1. 定位接口入口

从 METHOD、PATH、Handler 名或调用方反向搜索，确认完整链路：

```text
路由注册 -> Handler/Controller -> 请求绑定/校验 -> Service/Domain
                                      -> 响应 DTO/Assembler -> 统一响应信封
```

不能只找到路由字符串就停止，也不能只找到同名 DTO 就假定该接口使用它。

### 2. 核对请求字段

逐项确认：

- JSON/form/query/path 中的真实字段名
- Go/Java/TypeScript 等语言类型与序列化类型
- 指针、nullable、optional、默认值
- validate/binding tag 和手工校验
- 嵌套对象与数组元素结构
- 同名字段在不同入口是否语义不同

“必填”以真实绑定和校验行为为准。字段为非指针不一定等于业务必填；继续检查默认值和手工校验。

### 3. 核对响应字段

沿实际返回分支确认：

- 返回 DTO 或序列化 struct
- 直接构造的 map/anonymous object
- Assembler/Converter/Builder
- 条件字段、omitempty 和空值行为
- 公共响应信封
- 不同业务分支是否返回不同结构

如果 DTO 声明字段但实际构造从不赋值，也要记录当前运行时行为，不能只抄类型定义。

### 4. 核对调用方

已有 RPC 或公共 HTTP 接口至少检查一个真实调用方，用于确认：

- 接口分类是否正确
- 请求字段如何传递
- 响应字段是否被消费
- 修改字段会影响哪些 Git 仓库

找不到调用方不代表接口不存在，但必须在影响分析中注明搜索范围。

## 数据库核对

对每张已有表确认：

- 真实表名和数据库名
- 主键、关联键和关键索引
- 字段名、数据库类型、可空性、默认值
- ORM 模型字段、column tag 和类型转换
- 生效迁移顺序
- 软删除、时间字段和公共基类带来的隐式字段

模型与迁移不一致时：

1. 确认是否存在后续迁移或兼容代码。
2. 在核对记录中并列模型和迁移证据。
3. 无法判断线上真实结构时标记 `有冲突` 或 `待确认`，不自行修正文档。

ER 图中的新增字段来自目标设计；已有字段来自代码证据。不要用目标 DDL 反向证明当前已经存在。

## MQ 核对

至少搜索并确认：

- Topic 和 Tag 常量
- 生产者发送位置与条件
- 实际序列化的消息类型
- 消费者注册和过滤条件
- 消费端反序列化类型
- 消息版本、可选字段和兼容策略

生产与消费 payload 不一致时标记 `有冲突`。只有消息文档、没有代码时不能写 `已核对-现有`。

## 字段差异判定

先生成内部差异矩阵：

| 字段路径 | 当前代码 | YApi | 目标需求 | 结论 | 状态 |
|---|---|---|---|---|---|

判定规则：

- 三方一致：按代码事实写入，状态 `已核对-现有`。
- 代码存在、目标不变：变更类型 `-`。
- 代码存在、目标变化：保留当前证据，状态 `待实现-修改`。
- 代码不存在、目标明确新增：状态 `待实现-新增`。
- 只有 YApi 存在：不能判断为当前实现；继续搜索或标记冲突/待确认。
- 只有示例 JSON 存在：仅作为样例，不用于确认完整契约。
- 需求未提、代码中存在：完整契约仍需保留，变更类型 `-`。
- 目标要求删除字段：标记 `删除`，补充调用方影响和兼容策略。

## 证据记录

代码证据使用稳定可搜索的表达：

```text
<仓库相对路径>:<符号或类型.字段>
```

示例：

```text
router/order.go:RegisterOrderRoutes
dto/order.go:DetailRequest.OrderID
dto/order.go:DetailResponse.Items[].ClassID
service/order.go:BuildDetailResponse
models/order.go:Order.Status
mq/order_event.go:OrderCreatedMessage.OrderID
```

不要只写“见代码”“参考 DTO”或一个目录名。行号可以补充，但不能替代符号。

## 阻断条件

出现以下任一情况时，不得将相关后端字段标为已确认：

- 无法访问后端仓库或不能确定分支
- 找不到接口真实路由或 Handler
- 找到 DTO，但不能证明目标接口实际使用它
- 响应通过动态结构生成且无法展开
- 模型、迁移或多个分支互相冲突
- MQ 只找到生产或消费单侧，且契约无法互证
- YApi 与代码字段、类型或必填性不一致
- 需求要求“保持原逻辑”，但找不到对应实现

将需求歧义、业务口径冲突或验收缺口写入同目录的 `需求澄清问题列表.md`。代码仓库、分支或模块范围无法定位时先交互式询问用户；在取得必要代码前，不得把相关现状字段标为已确认，也不得声称概要设计已完成。
