# High-Level Design

基于已确认需求和真实代码，形成前后端可共同评审的概要设计。重点回答改动哪些 Git 仓库、仓库如何协作、关键数据与状态如何变化、跨仓契约如何演进，以及如何发布、验证和回滚。不要展开函数级实现、完整 DDL、字段全集或逐条测试方法。

## 阶段边界

- 上游输入是原始 PRD、已确认的需求澄清结论和适用的设计材料。
- 主产物只有 `worktree/<需求名>/docs/概要设计文档.md`；当前目录就是需求目录时使用 `docs/概要设计文档.md`。
- 发现新的需求歧义、业务口径冲突或验收缺口时，允许更新统一的 `docs/需求澄清问题列表.md`。这是跨阶段协作副作用，不是新的概要设计产物。
- 下游详细设计按概要设计确认的 Git 仓库边界分别展开实现方案。
- 不自动进入详细设计。只有用户明确确认概要设计完成后，才由阶段命令准备需求工作树并进入统一的 `detailed-design` 入口。

## 知识与资源路由

执行前读取 `knowledge/business/` 和 `knowledge/architecture/` 中与本需求相关的内容。不要为了满足形式读取或复述无关知识。

按任务需要读取以下资源：

- 定位工作区、Git 仓库、代码基线和证据时，读取 [工作区与证据规则](references/workspace-and-evidence.md)。
- 分析前端页面、路由和共享能力时，读取 [前端代码核对与概要设计边界](references/frontend-code-verification.md)。
- 分析后端接口、模型、数据库或 MQ 现状时，读取 [后端代码核对规则](references/backend-code-verification.md)。
- 发生 HTTP、RPC、MQ、配置或持久化结构变化时，读取 [契约与兼容性规则](references/contract-and-compatibility.md)。
- 涉及迁移、定时任务、灰度、价值类数据或高风险回滚时，读取 [风险专项规则](references/risk-guides.md)。
- 编写发布验证场景时，读取 [准入与验收场景规则](references/acceptance-scenarios.md)。
- 定稿前执行 [概要设计质量门](references/quality-gate.md)。

## 输入判断

必须读取：

1. 原始 PRD。
2. 存在的 `worktree/<需求名>/docs/需求澄清问题列表.md`。
3. 当前工作区内与需求相关的真实代码。
4. 能够证明目标方案或现状的其他材料。

原型、UI 图和交互说明按影响范围判断：

- 涉及页面、视觉状态或交互变化时，必须读取能够覆盖相关变化的设计源；缺失时向用户索取，不得猜测。
- 能从需求范围和代码证据确认不涉及前端变化时，标记为不适用并记录依据，不因 PRD 未显式声明而阻断。
- 无法判断是否涉及前端变化时，定向询问用户。

流程状态文件为 `worktree/<需求名>/docs/flow-state.json`。文件存在时读取流程上下文；不存在时独立执行当前阶段，不创建状态文件，也不把它记为材料缺失。阶段记录与当前入口不一致时提示，但不阻断当前阶段。

## 工作原则

- “模块”统一指经 Git 确认的仓库。页面、组件、路由、Service、数据表、任务和协议能力都不是模块。
- 同一 Git 仓库在“改动模块”表中只出现一行，仓库内全部变化合并描述。
- 只有需要修改代码、仓内资源、仓内脚本、页面、接口定义、任务定义或持久化结构的仓库才属于改动模块。
- 只使用现有后台或配置入口录入数据、且仓库自身无需变更的仓库属于依赖模块。
- 现状结论来自目标分支真实代码。PRD、YApi、历史设计和示例只能说明目标或候选信息，不能代替代码证据。
- 使用 `已核对-现有`、`待实现-新增`、`待实现-修改`、`有冲突`、`待确认` 区分事实状态。代码中找不到不等于本次新增。
- 只让会改变仓库边界、关键数据口径、跨仓契约或上线风险的问题阻断。普通技术选择依据现有架构和最简单可行方案决定，并记录理由。

## 设计深度

概要设计必须覆盖：

1. 业务目标、范围和明确不做什么。
2. 改动仓库、依赖仓库及各自职责边界。
3. 核心用户旅程、关键状态变化和跨仓数据流。
4. 发生变化的跨仓契约、责任方和兼容策略。
5. 适用的历史数据、权限、事务、幂等、性能、迁移、灰度和第三方风险。
6. 发布顺序、回滚条件、准入场景和业务验收场景。

不要在概要设计中展开：

- 未变化的完整请求、响应、DTO 或消息字段全集。
- Props、Events、store、hooks、CSS 参数和组件文件清单。
- 函数、类、内部变量、完整 SQL、完整 DDL 或实现伪代码。
- 固定重试参数、批量大小和告警阈值等尚需压测或详细设计确认的实现参数。

变化的字段、枚举、层级或语义必须写清变化内容、兼容方式和责任方；未变化部分引用当前代码位置。

## 输出结构

使用 [概要设计模板](assets/high-level-design.md)，固定保留五章：

1. `一 需求概述`
2. `二 核心方案`
3. `三 仓库协作与契约变化`
4. `四 影响与风险`
5. `五 发布与验证`

状态机、页面方案、ER、定时任务、迁移、灰度与可观测性只在影响概要决策时，作为对应核心章节下的扩展小节加入。不要恢复旧版八章结构，也不要为了填满模板生成大段“无”。

文档内代码路径统一写成 `<Git 仓库目录名>/<仓库内相对路径>:<符号>`。不得出现 `/Users/...`、Windows 盘符等本机绝对路径。仓库外材料使用相对产物位置的路径并标注“仓库外材料”。

状态文件存在时，只把 `docs/概要设计文档.md` 写入 `stages.high-level-design.output` 或 `outputs`，不得新增其他产物字段。阶段确认前不要把状态标记为 `completed`。

## 执行流程

1. 定位需求目录、可选状态文件、PRD、统一问题列表、相关设计材料和代码仓库。
2. 读取相关业务与架构知识，确认 Git 仓库边界、分支、commit 和工作区状态。
3. 建立“需求目标 → Git 仓库 → 关键变化 → 跨仓契约 → 风险 → 验证场景”的追踪关系。
4. 对阻塞概要决策的问题定向询问，并更新统一问题列表。
5. 使用五章模板生成或更新 `概要设计文档.md`，按适用风险加载专项规则。
6. 执行质量门和 `scripts/validate_high_level_design.py`。
7. 重新读取产物，检查仓库边界、契约、风险、场景和跨章节一致性。
8. 告知用户阻塞项、核对范围、校验结果和产物绝对路径，等待用户确认。

## 交付标准

- 改动仓库和依赖仓库明显区分，同一仓库的职责在各章节保持一致。
- 核心方案足以让产品、前端、后端和 QA 共同 Review，但没有侵入详细设计。
- 每个变化的跨仓契约都有变化内容、兼容策略和责任方。
- 适用风险有明确结论；不适用项无需机械展开。
- 准入场景覆盖进入验收前的关键门槛，验收场景覆盖用户可观察的需求结果。
- 文档没有本机绝对路径、旧版八章标题、空白模板或无依据的猜测。
- 结构校验脚本通过，最终文件已重新读取确认。

## 兼容旧问题清单

仅在 `worktree/<需求名>/docs/` 检查旧文件 `requirement-question-list.md`。只有旧文件存在且 `需求澄清问题列表.md` 不存在时，才将其重命名为中文文件名，并同步状态中的需求澄清输出字段。两个文件同时存在时不要覆盖或合并，先询问用户。
