# Requirement Clarification

读取需求材料、业务知识和真实代码，识别会改变产品行为、用户体验、验收口径、数据正确性或系统边界的问题。唯一产物是 `需求澄清问题列表.md`。本阶段不生成、改写或补全 PRD，也不做技术设计。

## 输入与边界

必须读取：

1. 原始需求文档。
2. `knowledge/business/`。
3. 与需求相关的真实前端、后端、公共组件和上下游实现。

按需读取原型、UI 图、问答记录、流程图、接口文档和其他版本的需求文档。PRD 引用的图片必须实际读取；无法读取时记录材料缺失及影响，不能用“字段如图所示”代替检查。

代码库是存量需求的准入条件。未定位相关入口、数据结构或核心业务逻辑前，不得完成审查或生成最终问题列表。工作区和代码定位规则见 [工作区与代码定位](references/workspace-discovery.md)。

只记录需要人作出业务判断的问题。数据库字段命名、缓存、索引、并发控制实现、日志级别等纯实现选择留给设计阶段。

## 流程状态

完整流程的唯一状态文件是 `worktree/<需求名>/docs/flow-state.json`。

- 文件存在时，读取 `currentStage` 和 `stages.requirement-clarification`；阶段不匹配只提示，不阻断独立执行。
- 文件不存在时，按当前阶段独立执行，不创建状态文件，也不把状态文件缺失写成材料问题。
- 状态文件存在时，只能更新 `stages.requirement-clarification.status`、`confirmed`、`output`、`outputs`、`blockedReason` 和 `currentStage`。
- 不得新增 `codebasePaths`、`outputPath`、`artifact`、`artifacts` 或其他字段。

需求澄清通常发生在 `flow-state.json` 创建之前，因此完整流程中以集中产物和用户确认为主要完成依据。

## 产物

唯一输出：

```text
worktree/<需求名>/docs/需求澄清问题列表.md
```

当前工作区就是需求目录时，路径为 `docs/需求澄清问题列表.md`。不得写入原始 PRD、业务仓库的 `docs/`、`.claude/docs/` 或 `codebase/`。

使用 [问题列表模板](assets/需求澄清问题列表.md)。产物中的材料和代码路径统一写成 `<Git 仓库目录名>/<仓库内相对路径>`，不得写本机绝对路径。

## 优先级

- `P0`：不确认就无法确定业务目标、核心流程、关键数据正确性或目标仓库边界，阻断整个概要设计。
- `P1`：不确认会影响接口契约、验收结果、历史数据、权限、灰度、回滚或上线安全，阻断受影响的设计内容。
- `P2`：不影响核心方案，可以延后确认或采用明确默认值，但必须记录责任人和确认时点。

优先处理 P0，再处理 P1。每轮向用户提出 1 至 3 个相互独立的业务决策。

## 执行流程

### 1. 读取材料和业务知识

完整阅读有效版本的 PRD、补充材料和 `knowledge/business/`，提取：

- 业务问题、目标用户、期望结果和范围。
- 角色、术语、渠道、时间和灰度口径。
- 正常流程、状态、异常分支和验收结果。
- 字段、枚举、筛选项、默认值、按钮和文案。
- 已有问答及其来源。

无法判断材料版本是否有效时，形成问题，不自行选择版本。

### 2. 定位并核对真实代码

执行 [工作区与代码定位](references/workspace-discovery.md)。至少核对：

- Router/Controller 的入口、参数和响应。
- DTO/Model 的字段、类型、枚举和默认值。
- Service/Domain 的校验、状态流转、异常和业务边界。
- 前端页面的展示字段、按钮状态、筛选项和交互文案。
- 公共组件、调用方和下游系统的责任边界。

代码依据必须包含仓库相对路径和具体符号、字段或接口。只写“代码中已有”不算有效证据。

### 3. 执行完整性审查

读取并执行 [需求审查清单](references/review-checklist.md)。重点识别：

- 目标与功能是否一致。
- 核心数据从哪里产生、由谁维护、何时生效、谁消费、如何失效和审计。
- 金钱、积分、余额、额度、权益次数等价值变化是否有流水、冲正和对账规则。
- 正常、异常、权限、状态、字段、文案和验收规则是否完整。
- PRD、原型、代码和不同版本材料是否冲突。

对核心规则用 EARS 语义检查触发事件、成立条件、持续状态和业务可观察结果，但最终只记录发现的问题，不生成 EARS 规格。

### 4. 按需执行兼容性检查

需求涉及 API、JSON、消息体、数据库 JSON、快照、配置、缓存结构、Prompt 输出或持久化模型变化时，必须读取并执行 [兼容性与演进检查](references/compatibility-and-evolution.md)。

不能因为 PRD 没有升级方案就跳过兼容、历史数据、迁移、混部、灰度或回滚。缺失本身就是待确认问题。

### 5. 发起定向询问

读取 [问题编写与交互规则](references/question-quality.md)。每个问题只包含一个业务决策，并写清：

- 问题是什么。
- 材料或代码依据。
- 不确认会造成什么影响。
- 哪个人类岗位或团队角色负责确认。

用户暂时无法回答时保留为 `待确认`，不得替用户选择。用户答复后，将答复、来源和状态更新到同一问题列表。

### 6. 生成并复核问题列表

按 P0、P1、P2 排序并合并重复问题。即使没有发现问题，也要在已经完成代码核对的前提下生成文件，写明检查范围和“本轮未发现待确认问题”。

关键风险检查至少覆盖：

- PRD 目标与功能对齐。
- 核心数据全链路。
- 价值类数据流水。
- API/JSON 契约兼容。
- 历史数据和存量快照。
- 数据迁移或重算。
- 新旧版本混部。
- 灰度发布。
- 回滚兼容。

写入后重新读取产物，确认问题统计、检查范围、材料状态、依据、影响、答复和状态完整，并检查没有本机绝对路径。

## 完成标准

- 已完整读取原始材料、可用图片、业务知识和相关代码。
- 已定位与 PRD 对应的真实入口、数据结构或核心业务逻辑。
- 每个问题都有依据、影响、优先级和建议确认人。
- 已区分待确认问题和已确认问题。
- 已生成并重新读取 `worktree/<需求名>/docs/需求澄清问题列表.md`。
- 最终回复说明是否存在待确认问题、P0/P1/P2 数量、检查范围和产物绝对路径。

用户确认阶段完成后，状态文件存在时将本阶段标记为 `completed`，把 `currentStage` 更新为 `high-level-design`；状态文件不存在时不创建，直接提示可以进入概要设计。
