# 兼容性与演进检查

适用于 API、JSON、数据库 JSON 字段、快照、配置、消息体、缓存结构、Prompt 输出结构或持久化模型变化。

先从代码中定位数据生产方、消费方、序列化和反序列化结构、持久化位置及调用关系，再检查以下内容。

## 契约差异

列出新增、删除、改名、类型变化、层级变化、必填性变化、默认值变化和枚举语义变化。只写“扩展 JSON”不算完成。

## 读写兼容

分别确认：

- 新代码读取旧数据。
- 旧代码读取新数据。
- 新旧服务混部。
- 缺字段、未知字段、`null`、空数组和非法枚举的表现。

## 存量数据

明确历史记录、历史快照、进行中流程和缓存数据升级后的用户可观察结果。需要确认沿用旧口径、补齐、重新计算、迁移还是不可用。

## 数据迁移

需求阶段确认是否需要处理、数据范围、生效时间、完成判定和失败后的业务表现。批处理、懒迁移或展示层推导等实现方式留给设计阶段。

## 灰度与混部

确认灰度对象、开关维度、新旧逻辑并存规则、观察指标、扩大条件和停止条件。没有灰度方案时，确认是否接受全量上线风险。

## 回滚兼容

确认新版本已经写入的新结构能否被旧版本读取，以及回滚期间新旧数据如何展示和继续处理。

## 上下游版本

确认调用方、下游、离线任务和数据分析是否依赖旧字段或旧语义，是否需要版本号、双写、双读或协同发布。

以下问题必须独立判断，不能合并成“是否考虑兼容性”：

- 新结构是否破坏旧消费者。
- 历史数据是否能被新代码读取。
- 历史数据升级后的业务口径。
- 新旧版本混部和回滚是否安全。
- 是否需要灰度以及灰度停止条件。

适用但无法得出结论时形成具体问题。不适用或无风险时，也要在问题列表的关键风险检查中记录依据。
