# 验证与开发准入

## 验证计划

从概要设计的 AC/VC 场景中选择当前仓负责或参与的场景，并补充仓内实现风险场景。每个场景记录来源、可观察结果、验证层级和优先级。

验证层级使用：

- `api-entry`：HTTP、RPC、MQ、任务等真实入口行为。
- `page-mock`：稳定 mock 条件下的页面与交互行为。
- `unit`：复杂纯逻辑、状态计算、解析器或缺陷修复。
- `integration-e2e`：跨仓、真实依赖或连续业务流程。
- `manual`：当前无法自动化且有明确人工步骤和证据要求。

不要把数据库写入、MQ 发送或缓存更新本身当作业务验收结果，除非它就是下游可观察契约。

## 最小完成标准

- 仓库、kind、分支、commit、工作区和核对范围可追溯。
- 当前事实有代码证据，目标变化有需求或概要依据。
- 本仓职责、不做什么、文件落点和复用决策明确。
- 完整最终契约足以直接实现，跨仓双方定义一致。
- 权限、事务、幂等、并发、异常、兼容和资源释放按适用性收口。
- 每个关键场景都有验证方式和可观察结果。
- 风险、待确认项、允许范围和禁止范围明确。

## 准入结论

- `可实施`：全部最小完成标准满足，没有阻断实施的问题。
- `部分可实施`：部分范围完整，但仍有明确阻断范围；可以继续完善设计，不能完成 DevFlow 详细设计阶段。
- `阻断`：无法建立可信范围、完整契约或关键实现方案。

一个仓库的结论不能代替整个阶段结论。只有全部目标仓库均为 `可实施`，统一入口完成跨仓一致性检查并获得用户确认后，才能进入实施阶段。
