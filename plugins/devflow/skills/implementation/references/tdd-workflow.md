# Go 风险分级验证工作流

测试类型和 Mock 边界以 `knowledge/engineering/testing.md` 为准。严格 RED/GREEN 只用于复杂纯逻辑、状态计算、解析器、算法和缺陷修复，不是所有实施任务的默认流程。

本规范是 `implementation` 的后端内置执行规则。开发每个后端计划任务时，严格执行以下循环，不依赖外部 skill 或 agent。

## 1. 基本循环

对一个最小可观察行为依次执行：

1. **RED**：先写一个描述目标行为的最小测试。
2. **Verify RED**：立即运行该测试，确认它因目标行为尚未实现或行为错误而失败。
3. **GREEN**：只编写让当前测试通过所需的最小生产代码。
4. **Verify GREEN**：重新运行当前测试及直接关联测试，确认全部通过。
5. **REFACTOR**：仅在 GREEN 后消除重复、改善命名或拆分过长函数，随后再次确认 GREEN。
6. 进入下一个最小行为，重复上述步骤。

不得先批量写完测试再批量实现，也不得先完成生产代码再补测试。

## 2. 有效 RED

有效 RED 必须同时满足：

- 测试能够完成编译和初始化并进入目标断言或预期调用。
- 失败原因与当前要实现的行为直接相关。
- 失败信息能够说明缺失行为或错误结果。

以下情况不算有效 RED，修复后必须重新运行：

- 测试首次运行就通过。
- 语法错误、编译错误、缺少依赖或 import 错误。
- 测试环境、数据库连接、端口或权限错误。
- mock 配置错误导致未进入被测业务逻辑。
- 因无关历史用例失败而退出。

如果目标行为已经存在，不要制造无意义失败。应补充能暴露本次缺陷、边界或回归风险的测试；若详细设计中的验收行为已完整存在且无法形成有效 RED，停止该任务并向用户报告已验证事实，不得伪造 RED。

## 3. 最小 GREEN

- 只实现当前测试要求的行为，不提前扩展未被验收约束覆盖的能力。
- 测试失败时优先修复生产代码；只有测试与详细设计不一致时才修改测试。
- 不顺手重构无关模块，不引入与当前行为无关的抽象。
- 当前测试通过后，运行直接关联测试，防止局部 GREEN 掩盖回归。

## 4. 既有代码修改

修改既有实现时保留现有代码，不机械删除后重写。先添加能复现缺陷或表达新增行为的测试，观察有效 RED，再做最小修改。

重构任务先确认现有行为有测试保护。若现有测试不足，先补 characterization test 并确认其 GREEN，再为需要改变的行为进入新的 RED 循环。

## 5. 后端入口测试

- 从详细设计指定的 HTTP、MQ、Domain Command 或定时任务入口发起测试。
- 验证最终可观察结果，不断言内部 helper 调用、临时变量或对象创建等实现细节。
- 一个测试或子 case 聚焦一个行为，名称与详细设计中的测试方法名一致。
- table-driven case 必须让每一行输入与预期结果清晰对应。
- 优先使用仓库已有测试 helper 和断言方式，不重复搭建测试基础设施。

## 6. Mock 边界

只 mock IO 和进程边界，不 mock 被测入口内部的业务链路：

- MySQL：使用项目已有 MySQL mock helper 和 sqlmock。
- Redis：使用项目已有 Redis mock helper。
- 外部 API：使用项目已有 API client mock 封装。
- MQ：使用项目已有 MQ mock helper。

不得 mock controller 调用的 service、service 调用的 domain command 等内部实现来代替入口链路验证，除非现有架构已把该调用明确设计为外部边界。

## 7. 执行证据

每个测试方法至少保留以下信息，供 `docs/implementation/<仓库名>/test-report.md` 汇总：

| 字段 | 要求 |
|---|---|
| 测试方法 | 与详细设计完全一致 |
| RED 命令 | 实际执行的精确命令 |
| RED 结果 | 关键失败原因，证明是有效 RED |
| GREEN 命令 | 实际 fresh 执行的精确命令 |
| GREEN 结果 | 通过数量和 exit code |

不需要在报告中粘贴完整终端输出，但执行者必须读取完整输出并确认 exit code。所有任务需要 fresh 验证证据；只有选择严格 TDD 的任务需要 RED/GREEN 证据。
